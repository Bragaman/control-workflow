# Независимое агентское ревью

Управляющий вызывает subagent своим инструментом, без нового таба herdr.
CLI сохраняет протокол; исполняющего диспетчера в панели нет. `reviewer` задачи —
приёмщик, `actor` попытки — уникальное имя проверяющего subagent. Успешное ревью оставляет
задачу в review. Complete, merge и push требуют отдельного поручения пользователя.

## Отправить результат на проверку

Используй выбранные state/config/bindings из [control-entry.md](control-entry.md).
Команды ниже — подкоманды control.py с этими параметрами.

1. Прочитай задачу и текущий запуск. Для no-code проверь состав результата:
   исполнитель передаёт файлы/каталоги через `finish --artifact PATH` (флаг повторяется).
   Сам result.md входит всегда. Если артефакты не были указаны при finish,
   добавь их через `review-request --run RUN --artifact PATH` (флаг повторяется). Проверка инфраструктуры требует наблюдений живой системы
   с временем и областью доступа; хеш отчёта не доказывает её состояние.
2. Выполни `review-request --run RUN`. Повтор возвращает ту же активную попытку.
   Используй возвращённую попытку: pending ещё не означает запущенного проверяющего.
   Отдельный review-show после request не нужен. Для просмотра без запроса —
   `review-show --run RUN --latest`; без --latest доступна вся история.
   При running проверь уже назначенного actor; при актуальных passed/changes_requested
   используй сохранённое заключение. Новый subagent нужен только для pending.
3. Выбери уникальное имя subagent и заранее закрепи попытку командой
   `review-claim --run RUN --id REVIEW --actor AGENT` с этим именем.
   Только управляющий, успешно закрепивший pending, запускает проверяющего.
   При running прочитай сохранённый actor и проверь существующего subagent;
   повтор claim того же actor возвращает прежнюю аренду, запускать ещё одного нельзя.
4. Запусти свежий subagent с закреплённым именем без наследования переписки
   (`fork_turns="none"`). Передай путь packet, ID попытки, полную команду control.py с выбранными
   state/config/bindings и цель независимой проверки.
   Поручи читать сохранённые инструкции, проверять критерии самостоятельно и вернуть
   JSON. Проверяющий не исправляет результат и не запускает команды принятия.
   Исходный отчёт — предмет проверки. При сбое запуска сохрани failed через conclude
   либо дождись аренды. Аренда по умолчанию 900 секунд, `--lease` допускает 1–3600.
   Выполни conclude до её окончания.
5. Сохрани ответ в отдельный JSON и выполни
   `review-conclude --run RUN --id REVIEW --actor AGENT --result FILE`.
   Поля: version, status, conclusion, findings, suggestions, evidence, limitations.
   Последние четыре — списки строк. evidence обязателен; findings содержит обязательные
   исправления. status: passed, changes_requested или failed. Отсутствующие необходимые
   доказательства означают failed. Необязательные предложения запиши в suggestions.
6. Покажи пользователю заключение, доказательства, ограничения и свежесть проверки.
   Изменение файлов или критериев делает старую проверку stale. Запроси новую версию
   командой review-request. Ответ старой попытки не может завершить новую.

Начни чтение с `review-read --run RUN --id REVIEW`: entry содержит критерии,
версию, ссылки на сохранённые инструкции и отчёт, границы и список репозиториев.
Выбирай материалы командами с теми же --run и --id:

- `--section files` — все исходные пути, SHA-256, режимы и пути blobs;
- `--section diff --repository 0` — base/head, status и diff выбранного worktree;
- `--section blob --path /source/path` — выбранный файл; бинарный доступен по stored_path;
- `--section manifest` — полный snapshot.json для прежних потребителей.

Все разделы выводятся из фиксированного снимка после проверки его хешей;
живые файлы не подставляются. Entry помогает выбрать чтение, но все критерии
и необходимые доказательства проверяются полностью. Старые снимки читаются теми
же командами без миграции. Прямое чтение snapshot.json и blobs также сохранено.

Пакет содержит исходное задание, критерии, инструкции, result.md и явно выбранные
артефакты в blobs с SHA-256. Кодовый снимок дополнительно содержит base/head,
diff, status и содержимое tracked/untracked файлов всех worktree. Ignored-файлы
не входят; необходимые генерируемые результаты передай через --artifact.
Символические ссылки сохраняются как ссылки: внешнюю цель передай отдельно,
если она входит в проверку. Секреты не передавай в артефакты.
Проверки выполняй в отдельном временном каталоге. После наблюдений живой системы
запиши время; последующие внешние изменения панель автоматически не обнаруживает.

## Доработать результат

Убедись, что исходный исполнитель доступен в исходном табе, затем выполни
`review-feedback --run RUN --id REVIEW` для changes_requested. Команда сохраняет
возврат, сразу переводит тот же запуск в running и возвращает feedback_message
в исходном объёме assignment.md. Доставь сообщение этому исполнителю и подтверди
`review-feedback --run RUN --id REVIEW --delivered`.

Исполнитель может выполнить finish ещё до подтверждения доставки. Подтверждение
только записывает факт доставки; оно не переводит уже сданную работу обратно
в running и принимается даже после создания следующей auto-проверки.
Повтор подготовки или подтверждения возвращает сохранённую запись.
При сбое доставки повтори её для того же исполнителя; исчезновение исполнителя
и спорные требования передай пользователю. Второго исполнителя поверх живого
не запускай. Если подготовка была прервана ошибкой, повтори review-feedback
до отправки сообщения: команда восстановит незавершённый переход, включая
ошибку записи task после сохранения run. Подготовленные старой версией сообщения
мигрируются при повторе подготовки или подтверждении доставки.

На запуск разрешены два автоматических возврата. Цикл учитывается при подготовке,
даже если подтверждение доставки потерялось. После лимита решение принимает
пользователь. По явному поручению пользователя продолжить, в том числе после
failed с конкретными замечаниями, используй `review-feedback --user-requested`.
Такое поручение сохраняется отдельно и не считается автоматическим циклом.
Сам по себе failed не разрешает автоматическое возобновление.

Каждый finish увеличивает номер сдачи, включённый в версию снимка. Поэтому новая
сдача даже тех же файлов получает новую проверку, а повтор review-request одной
сдачи возвращает прежнюю попытку. После finish повтори request/claim/conclude.
Passed по-прежнему оставляет review для приёмщика.

## Политика и сбои

`task-create` и `task-set --agent-review-policy off|manual|auto` задают политику
одной задачи. Старые задачи работают в manual без миграции.

| Политика | После finish |
| --- | --- |
| off | Результат в review, review-request запрещён |
| manual | Результат в review, запрос по поручению пользователя |
| auto | Результат в review и сохраняемый pending; обработка активным управляющим при следующем взаимодействии |

Auto сам не создаёт subagent и не гарантирует срок начала. Управляющий при обращении
к выбранной auto-задаче проверяет review-show, подхватывает pending и проводит
разрешённые циклы. Auto не включается массово для существующих задач.
Если снимок после finish создать не удалось, finish сохраняет результат и
agent-review-error.json; управляющий устраняет причину и повторяет review-request.

Исчезнувший subagent остаётся running до срока аренды. review-show, review-request
или другая команда review переводит истёкшую аренду в failed. Это проверка срока
при обращении, отдельного фонового таймера нет. После сбоя запрос создаёт новую
попытку; позднее заключение прежнего агента отвергается. История хранится в
runs/RUN/agent-review.json и reviews/REVIEW, состояние задачи не подменяется.
