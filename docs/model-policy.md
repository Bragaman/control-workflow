# Переносимая политика моделей

Подключи политику в config экземпляра. Значение `builtin` выбирает поставляемую
[config/model-policy.json](../config/model-policy.json); можно указать свой JSON.
Относительный путь разрешается от каталога config, независимо от cwd.
Для собственного JSON возьми за основу поставляемый config/model-policy.json.
Политика содержит только schema_version, profiles и rules: её можно хранить
в Git и использовать в нескольких экземплярах. Пути, адаптер, подключения,
авторизация и ограничения аккаунта остаются вне политики.

```json
{
  "schema_version": 1,
  "adapter": "herdr-codex",
  "model_policy": "builtin",
  "model_overrides": {
    "profiles": {"luna": {"reasoning_effort": "high"}},
    "rules": {"planning": {"normal": "terra"}}
  }
}
```

Местные model_overrides рекурсивно дополняют выбранную политику по полям.
В примере изменены один effort и одно правило; остальные профили, правила
и настройки экземпляра сохраняются. Политика из файла должна быть полной;
overrides могут быть частичными. Имена профилей — идентификаторы панели;
`auto` зарезервировано. Каждый профиль задаёт явные model и reasoning_effort.
Неизвестные поля политики, ссылки на отсутствующий профиль, пустая модель,
пробельные/управляющие символы в именованном model и неподдержанный адаптером effort
дают ошибку. Идентификатор модели задаётся в формате провайдера: допустимы,
например, Claude sonnet[1m] и Bedrock ARN. Старые profiles сохраняют проверку
на непустую строку. Поддержку идентификатора и конкретной пары model/effort
проверяет провайдер.

Приоритет выбора для нового запуска:

1. Параметр `open TASK --profile NAME` или `start TASK --profile NAME`.
2. Явный профиль задачи из task-create/task-set.
3. Правило политики для типа и сложности задачи.
4. Без подключённой политики и явного профиля — прежняя матрица profiles
   из config поверх встроенных defaults.

Явный профиль доступен и в старом экземпляре: используется именованная встроенная
политика. Чтобы изменить её, подключи model_policy. Один вызов open с несколькими
ID применяет разовый профиль ко всем выбранным задачам.

```sh
control-workflow task-create demo --project lab --title 'Правка текста' --goal 'Уточнить инструкцию' --acceptance 'Проверена по источникам' --no-code --task-kind implementation --profile terra
control-workflow task-set demo --profile sol
control-workflow task-set demo --profile auto
control-workflow open demo --profile sol-high
```

`--profile auto` в создании/правке возвращает задачу к правилам; в open/start
укажи конкретное имя или опусти параметр. Выбирай тип по основной работе, а сложность — по неопределённости задачи. У задачи хранятся profile, profile_source и предварительные model/effort.
Профиль с источником rule пересчитывается по актуальным правилам при новом запуске.
Явное имя задачи сохраняется, а его model/effort разрешаются заново из политики.
Разовый выбор влияет только на запуск и не меняет задачу.
Запуск сохраняет profile, фактические model/effort и model_selection с источником
выбора, путём политики либо builtin/legacy-config и признаком местных overrides.
Это снимок параметров, переданных CLI агента; дальнейшее ручное переключение
в интерфейсе агента панель не отслеживает.

Повторное открытие работающего или подготавливаемого исполнителя сохраняет снимок.
Явный запрос совместим, только если имя профиля и разрешённые model/effort
совпадают с запуском; для старого запуска без имени сравниваются model/effort.
Конфликт возвращается как action=error без запуска другого агента.
Для смены сохрани checkpoint, останови прежнего исполнителя, выполни interrupt
с причиной и выбери профиль нового запуска: [recovery.md](recovery.md). Запуск со статусом blocked продолжает
текущего исполнителя; review/done/cancelled возвращают результат, а запрос
профиля для этих статусов — ошибку.

Местный config может задать `allowed_models` — список разрешённых имён.
Выбор вне списка завершается ошибкой без подмены. Панель не проверяет квоту
и доступ аккаунта заранее; отказ провайдера обрабатывается обычным протоколом
ошибки запуска с сохранением запрошенных параметров. Автоэскалации и fallback нет.
Список моделей и допустимые effort проверяй в используемом клиенте.

CLI и MCP используют одинаковые параметры: строка profile в инструментах
task-create, task-set, open и start. Конфигурация MCP закрепляется при запуске
процесса: после изменения политики/config перезапусти MCP. Отделённый подготовитель
использует сохранённые model/effort из state.json без чтения политики: изменение,
удаление или повреждение её файла после разрешения профиля не меняет запуск.
Для исторического запуска без полного снимка сохраняется чтение актуальной политики.
Разрешённые параметры записываются в state до подготовки терминала, чтобы дальнейшее
перечитывание состояния и совместимое повторное open --profile использовали тот же выбор.

## Миграция

Старые config/tasks/runs читаются без переписывания. Отсутствие model_policy
сохраняет прежние defaults и profiles; model=default оставляет выбор клиенту.
Для перехода сохрани прежний config, убери верхнеуровневый profiles и добавь
model_policy. Нужные исключения перенеси в model_overrides. Совмещать старый
profiles и новую model_policy запрещено: это ошибка с подсказкой миграции.
Проверь environment: он показывает выбранную политику и разрешённую матрицу.
Работающие исполнители сохраняют модели, существующие задачи без явного имени
выберут новые правила только при следующем запуске. Сохранённые снимки запусков
не мигрируются. Новая политика требует новую версию программы; перед откатом
программы верни старый config. Состояние поверх работающих агентов не откатывай.
