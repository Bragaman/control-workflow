# Регулярные задачи

Расписание хранится в выбранном `state-root` и содержит снимок выбранной задачи-шаблона. Расписание задаёт разрешённую для повторения работу; каждое срабатывание создаёт новую задачу и запускает её через обычный lifecycle. Приёмка и review остаются обязательными по настройкам задачи. Шаблон с зависимостями не поддерживается.

```sh
control-workflow --herdr-session SESSION schedule-create weekday-check \
  --template TASK_ID --days mon,tue,wed,thu,fri --time 09:00 --timezone Europe/Moscow
control-workflow schedule-list
control-workflow schedule-show weekday-check
control-workflow schedule-pause weekday-check
control-workflow schedule-resume weekday-check
control-workflow schedule-cancel weekday-check
```

При создании явно выберите экземпляр обычными параметрами state, bindings и config и работающую сессию herdr. Расписание привязано к её namespace и запускается только при совпадении namespace. Команда `schedule-tick` проверяет наступившие срабатывания; она требует тот же выбранный экземпляр и `--herdr-session SESSION` вне herdr. Программа не устанавливает фоновый scheduler. Для автоматической работы пользователь самостоятельно настраивает внешний периодический вызов tick на нужной машине. В выводе просмотра доступны режим внешнего tick и время последнего обычного tick (при восстановлении прерванного срабатывания оно не обновляется); отсутствие или давность проверки указывают, что автоматический запуск не подтверждён. Ошибки проверки namespace возвращаются вызывающему процессу; ошибки запуска задачи записываются в историю и в результат tick.

Tick рассматривает только последнее срабатывание за последние 24 часа, пропуская более старые. При возобновлении отсчёт начинается заново. Если предыдущая задача ещё не принята или не отменена, новое срабатывание записывается как пропущенное. Отмена расписания прекращает будущие срабатывания, но не останавливает уже созданную задачу. Tick и отмена сериализуются общей блокировкой: выигравший её tick может создать запуск до отмены.

При переходе часов несуществующее местное время пропускается; при повторе местного времени выбирается первое вхождение. База часовых поясов включена в бинарник и обновляется вместе с программой. История содержит время, задачу и запуск. После прерывания записи намерения запуска состояние `uncertain` требует ручной проверки задачи и запусков перед дальнейшими действиями; повторный tick автоматически не запускает её заново. До принятия или отмены этой задачи следующие срабатывания пропускаются; после ручной проверки при необходимости отмените задачу штатной командой task-set. Для сбоя с активным запуском используйте штатное восстановление запуска. При отказе запуска причина сохраняется в истории, а созданная задача остаётся для разбора.

## Linux: запуск через systemd user timer

Таймер вызывает tick через минуту после завершения предыдущей проверки, от имени пользователя, у которого работает herdr. Перед настройкой проверьте установку программы и доступ к нужной сессии. В примере программа установлена в `/opt/control-workflow`, сессия называется default. Замените эти значения и пути экземпляра на свои; `%h` в unit-файлах означает домашний каталог пользователя. Путь PATH должен включать каталоги herdr, Git и CLI выбранного агента.

Создайте файл `~/.config/systemd/user/control-workflow-tick.service`:

```ini
[Unit]
Description=Check control-workflow schedules

[Service]
Type=oneshot
Environment="PATH=%h/.local/bin:%h/.cargo/bin:/usr/local/bin:/usr/bin:/bin"
ExecStart=/opt/control-workflow/bin/control-workflow --program-root /opt/control-workflow --state-root %h/.local/state/control-workflow --bindings-root %h/.local/state/control-workflow/bindings --config %h/.config/control-workflow/config.json --herdr-session default schedule-tick
TimeoutStartSec=infinity
KillMode=process
```

KillMode=process сохраняет подготовители, запущенные командой tick, после завершения service. Они продолжают обычный запуск исполнителя.

Рядом создайте `control-workflow-tick.timer`:

```ini
[Unit]
Description=Check control-workflow schedules every minute

[Timer]
OnActiveSec=1min
OnUnitInactiveSec=1min
AccuracySec=1s
Unit=control-workflow-tick.service

[Install]
WantedBy=timers.target
```

На выбранной Linux-машине следующие команды проверяют файлы и включают пользовательский таймер. Ручной запуск service сразу обработает наступившие расписания, поэтому выполняйте его после проверки выбранного экземпляра и разрешённых шаблонов.

```sh
systemd-analyze --user verify ~/.config/systemd/user/control-workflow-tick.service ~/.config/systemd/user/control-workflow-tick.timer
systemctl --user daemon-reload
systemctl --user start control-workflow-tick.service
journalctl --user -u control-workflow-tick.service -n 30 --no-pager
systemctl --user enable --now control-workflow-tick.timer
systemctl --user list-timers control-workflow-tick.timer
```

Журнал содержит JSON-результат tick: проверяйте ошибки в items и истории срабатываний, даже если service завершился успешно. Если herdr недоступен или namespace изменился, задачи автоматически не запустятся. Расписание хранит своё время и часовой пояс; минутный таймер только проверяет его, поэтому запуск может произойти немного позже указанного времени.

Пользовательский systemd обычно работает в течение пользовательской сессии. Для запуска после загрузки без входа пользователя администратор может включить linger командой `sudo loginctl enable-linger USERNAME`. Это сохраняет пользовательский менеджер systemd, но herdr и его сессию тоже нужно запускать независимо от интерактивного входа.

Отключить будущие проверки:

```sh
systemctl --user disable --now control-workflow-tick.timer
```

Отключение таймера не прерывает текущий tick или уже работающих исполнителей. Чтобы остановить только одно расписание, используйте schedule-pause или schedule-cancel.

## Временные данные Workflow на Linux

Выбирайте state-root на диске. На arch-work подходит дисковый каталог
экземпляра панели. Команда `temp-exec` создаёт личный каталог
`STATE_ROOT/workflow-temp/RUN_ID` и задаёт временные пути для дочерней команды.

```sh
control-workflow temp-exec --run RUN_ID -- cargo test --locked
control-workflow temp-exec --run RUN_ID --slot base-build -- sh -c '
  checkout=$(mktemp -d) && git archive HEAD | tar -x -C "$checkout" &&
  cd "$checkout" && cargo test --locked
'
```

Второй пример собирает зафиксированный коммит HEAD. Для ревью восстановите
зафиксированные в снимке файлы кандидата по протоколу агентского ревью.
Подставьте полную команду выбранного экземпляра. TMPDIR указывает на рабочую
область слота, а Cargo, uv, Ruff и Python получают отдельные пути к кэшам.
Сохраняйте имя слота для совместимых повторов. В пустой слот нового запуска
переносится самый свежий подходящий кэш той же задачи. Промежуточные запуски
без кэша можно пропускать.
Если кэш занят, следующий вызов может повторить перенос, пока новый слот пуст.
Временный checkout останется в прежнем запуске. Отчёты и журналы сохраняйте
под runs.

Команда ждёт выхода потомков. Вспомогательный сервер для проверки запускайте
внутри той же команды и завершайте по окончании проверки. При завершении или
отмене задачи через complete панель останавливает процессы temp-exec, закрывает
принадлежащие задаче терминалы и чистит временные каталоги всех её запусков.
Если процесс, открытая ссылка или специальный файл помешали уборке, в
`temporary_cleanup` появится причина, а у задачи уже может быть конечный
статус. После сверки повторите исходную команду. Для отмены снова передайте
`--status cancelled`. Закрытые терминалы и завершённые Git-операции
сохраняются.

### Плановая уборка

`temp-sweep` удаляет выделенные каталоги через 24 часа после последней работы
с ними. Блокировка защищает активный temp-exec. Перед удалением файловые
аренды Linux защищают открытые и отображённые в память обычные файлы.
Ссылки на каталоги проверяются через /proc. Если обзор процессов
неполный, уборка сохраняет дерево и сообщает причину. Эта проверка
действует и при complete.
После аварийного выхода команды отсчёт может начаться с первого прохода,
на котором подтверждено, что каталог свободен.

Неизвестный владелец, отдельное монтирование или специальный файл оставляют
данные на месте. Запускайте уборку от владельца в PID namespace подготовителя,
обычно прямо на хосте. Файловая система должна поддерживать файловые аренды.
На время проверки аренды команда поднимает мягкий предел дескрипторов до
унаследованного жёсткого предела. Для большого дерева жёсткий предел должен
покрывать по одному дескриптору на обычный файл.

### Обзор процессов на Linux-хосте

На arch-work часть процессов закрывает cwd и открытые дескрипторы от
обычного пользователя. Для полной проверки администратор может установить
отдельную root-владеющую копию бинарника из принятого выпуска. Она запускается
в режиме чтения и возвращает только признак использования каталога. Основной
Workflow по-прежнему работает под UID владельца экземпляра и сам выполняет
удаление и остановку своих процессов.

Администратор копирует проверенный бинарник в
`/usr/local/libexec/control-workflow-temp-inspect`. Файл и все его родительские
каталоги должны принадлежать root. Используйте путь без символических
ссылок. Для файла задайте режим 0755, для каталогов исключите запись группы
и остальных. Обновляйте копию вместе с
основным бинарником. Используйте этот путь в отдельном файле sudoers,
отредактированном через `visudo -f /etc/sudoers.d/control-workflow-temp-inspect`.
Замените WORKFLOW_USER на имя владельца экземпляра.

```sudoers
WORKFLOW_USER ALL=(root) TIMEOUT=20 NOPASSWD: NOSETENV: /usr/local/libexec/control-workflow-temp-inspect _temp-inspect
```

Правило указывает точный исполняемый файл и единственный аргумент.
В существующем `runtime.json` выбранного bindings добавьте поле
`"temp_inspector": "/usr/local/libexec/control-workflow-temp-inspect"`.
Помощник проверяет UID вызывающего пользователя, номер inode и границы
каталога. При отказе sudo, подмене пути или ограниченном /proc очистка
сохраняет данные. Для отключения удалите поле из runtime.json, а затем
удалите правило sudoers и отдельную копию помощника.

### Таймер уборки

После обновления убедитесь, что установленная команда панели распознаёт
`temp-sweep --help`. Создайте
`~/.config/systemd/user/control-workflow-temp-sweep.service` и подставьте
постоянные пути экземпляра.

```ini
[Unit]
Description=Remove expired control-workflow temporary data

[Service]
Type=oneshot
ExecStart=/opt/control-workflow/bin/control-workflow --program-root /opt/control-workflow --state-root %h/.local/state/control-workflow --bindings-root %h/.local/state/control-workflow/bindings --config %h/.config/control-workflow/config.json temp-sweep
```

Рядом сохраните `control-workflow-temp-sweep.timer`.

```ini
[Unit]
Description=Check control-workflow temporary data hourly

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
```

Проверьте и включите таймер на хосте выбранного экземпляра.

```sh
systemd-analyze --user verify ~/.config/systemd/user/control-workflow-temp-sweep.service ~/.config/systemd/user/control-workflow-temp-sweep.timer &&
  systemctl --user daemon-reload &&
  systemctl --user start control-workflow-temp-sweep.service
journalctl --user -u control-workflow-temp-sweep.service -n 20 --no-pager
```

После успешного запуска service и проверки журнала включите таймер.

```sh
systemctl --user enable --now control-workflow-temp-sweep.timer
```

Остановить таймер можно командой
`systemctl --user disable --now control-workflow-temp-sweep.timer`.

### Разовая уборка старых кэшей в /tmp

Общесистемное правило systemd-tmpfiles остаётся в силе. Сборщик Workflow
работает в выделенном каталоге экземпляра. Для старых путей в /tmp нужны
`lsof` и доступ к процессам, которые могли открыть кэш. Остановите запуски и
проверки, использующие эти каталоги, и исключите новые обращения до окончания
уборки. При недоступности lsof или процессов отложите удаление.

1. Составьте список точных путей по журналам старых проверок. Сверьте владельца,
   назначение и выделенный объём каждого каталога. Пропустите каталоги
   неизвестного происхождения, символические ссылки и вложенные монтирования.
2. Из хостового PID namespace проверьте каждый путь через `lsof -nP +D "$path"`.
   Любая запись, ошибка доступа или неполный обзор процессов означает, что
   каталог пока нужно сохранить. Сокеты и другие специальные файлы требуют
   отдельной сверки.
3. Удалите по одному подтверждённому пути с помощью
   `rm -r --one-file-system -- "$path"` и проверьте освобождённое место.
   В качестве пути передавайте каталог конкретного кэша. Шаблоны по /tmp
   могут захватить данные других запусков.
