# Пути, настройки и данные

По умолчанию state расположен вне программы: Linux — XDG_STATE_HOME/control-workflow
(иначе ~/.local/state/control-workflow); macOS — ~/Library/Application Support/control-workflow/state. Для отдельного экземпляра укажи --state-root; установка
может быть доступна только для чтения. Каталог state создаётся при первой записи.
Справка и environment доступны без herdr. Исполнители запускаются через herdr. Степень проверки адаптеров указана в compatibility.md.

| Слой | Файлы | Выбор |
| --- | --- | --- |
| Программа | bin/, config/defaults.json, config/model-policy.json, docs/, skills/ | Физический путь bin/control-workflow; ресурсы доступны для чтения |
| Пользователь | JSON с model_policy, model_overrides (либо legacy profiles), adapter, git_mode, agent_start_timeout_ms, state_root, bindings_root | --config, затем CONTROL_PLANE_CONFIG, затем файл config ОС, если он есть; значения дополняют defaults.json |
| Машина | BINDINGS_ROOT/runtime.json, projects/ID.json и tasks/ID.json | --bindings-root, CONTROL_PLANE_BINDINGS, bindings_root из config, иначе STATE_ROOT/bindings |
| Состояние | projects/, tasks/, runs/, memory/, schedules/, notifications/, views/, status/, .control.lock | --state-root, CONTROL_PLANE_STATE, прежний CONTROL_PLANE_ROOT, state_root из config, иначе внешний каталог ОС |

Установленный бинарник определяет program_root как родитель bin. Для явного
выбора ресурсов используй --program-root или CONTROL_WORKFLOW_PROGRAM.
Программа, state, bindings и config выбираются независимо.

Пути state/bindings/runtime в JSON должны быть абсолютными. Путь model_policy
может быть относительным к каталогу config. Относительные пути параметров CLI и
переменных окружения разрешаются от текущего каталога. Для воспроизводимости
используй абсолютные пути. Дочерний процесс получает выбранные state/config/bindings
явными аргументами; запуск из собственного таба сохраняет их при complete.

Пользовательский JSON объединяется с defaults.json. В новом экземпляре подключи
политику и меняй отдельные поля через местные overrides:

```json
{
  "git_mode": "branch",
  "model_policy": "builtin",
  "model_overrides": {
    "profiles": {"terra": {"model": "my-model"}}
  }
}
```

Существование модели у провайдера не проверяется: конфигурацию выбирает
пользователь. Проверяются наличие имени, допустимый effort, Git-режим,
положительный таймаут и адаптер из списка herdr-codex, herdr-claude, hc-codex.
Неизвестный адаптер отклоняется до создания терминала.

runtime.json принимает herdr_executable, herdr_session, hc_executable, hc_session, cwd и worktrees_root.
Для проекта рабочий каталог меняется через project-set --cwd /path.
Если worktree нет, cwd проекта имеет приоритет над cwd машины; иначе используется
state. Репозитории, workspace, namespace и layout_pending проектов, а также
переопределения репозиториев задач записываются в bindings. CLI show объединяет
описание и локальную привязку. Исторические run сохраняют пути как свидетельство
своего запуска; это не переносимые настройки нового экземпляра.

Для нового кодового запуска Git создаёт worktree каждого указанного репозитория.
Первый worktree становится рабочим каталогом исполнителя и в адаптерах TUI открывается в Herdr
как дочерний workspace исходного репозитория. Родительские workspace сохраняются
в локальных bindings по репозиторию и namespace Herdr; обычный workspace проекта
остаётся для задач без кода. Остальные worktree перечислены в assignment и
переданы агенту как дополнительные каталоги, отдельные workspace для них не
создаются. Старые работающие запуски автоматически не перемещаются.

Старые смешанные project/task JSON продолжают читаться. При следующей записи
локальные поля сохраняются сначала в bindings, затем убираются из описания;
сбой между записями оставляет обе копии, и bindings имеют приоритет.
Для экспорта локальных полей выполни materialize-bindings: команда
дублирует локальные поля в прежние JSON под блокировкой, сохраняя bindings. Текущие
запуски, память и worktree не мигрируют и не удаляются. Переход нескольких файлов
не образует общей транзакции: после аварии сверяй run, task и binding.
Каждому state нужен собственный bindings_root; совместное использование одного
каталога bindings двумя state нарушает изоляцию.

Сводки сверок находятся в STATE_ROOT/status.

Отчёты finish и memory-add --file пересчитывают обычные Markdown-ссылки и
определения ссылок относительно нового файла; абсолютные пути, URL, anchors
и блоки кода сохраняются. Соседние артефакты остаются в исходном каталоге:
сохранение текста не копирует всю папку. Для вложенных скобок в пути используй
URL-кодирование, для пробелов — угловые скобки или %20. HTML и нестандартные
Markdown-конструкции не преобразуются.

Настройки config и runtime bindings имеют schema_version=1; неизвестная версия
отклоняется до внешних действий. Default config Linux — XDG_CONFIG_HOME/control-workflow/config.json
(иначе ~/.config/control-workflow/config.json); macOS — ~/Library/Application Support/control-workflow/config.json.
Если этот файл есть, он читается автоматически; явный --config имеет приоритет.
Отсутствующие bindings schema_version читаются как версия 1 для совместимости.

Именованные профили, приоритеты и миграция: [model-policy.md](model-policy.md).
## Результат и связь с сессией

`run ID --compact` и `open ID` для результата показывают структурированную
сводку этапов, препятствий и следующего шага. Приёмка берётся из текущей задачи,
публикация и очистка — из state, актуальность ревью проверяется по тому же
контракту, что и `review-show`. Флаг `stale` сохраняется рядом с исходным
статусом незавершённого ревью или замечаний; при недоступной проверке видна
ошибка. Повреждённые или устаревшие свидетельства видны
в сводке. Попытка ревью и ошибка создания снимка привязываются к номеру сдачи:
ошибка текущей сдачи не скрывается старым заключением, а после успешного нового
запроса прежняя ошибка не считается текущей. Для старой ошибки без номера
сдачи связь остаётся неизвестной. Время наблюдения и время изменения state указаны отдельно. Обычный
compact не обращается к удалённому Git: актуальность удалённой публикации,
установка и версия работающего процесса остаются unknown без отдельной проверки.
`launcher_alive` описывает подготовитель, а не исполнителя.

История операций и текст отчётов доступны через `run ID` и файлы запуска; команды
подробностей указаны в сводке. `current-result.md` остаётся доступным в полном
выводе, но его текст не используется как источник текущего статуса.

Для Codex herdr может вернуть agent_session. CLI сохраняет её только при
совпадении имени агента, вида, панели, таба, терминала и источника herdr:codex.
Отсутствие данных означает неподтверждённую связь; старые записи не дополняются
догадкой. Claude не поддерживает подтверждённый capture. Сохранение ID не
включает resume по ID. Полное state сохраняет исторический startup_error для
совместимости, компактное представление показывает его классификацию.

## Один терминал hc в трёх клиентах

На машине с Git-репозиторием и авторизованным Codex установите herdr-core.
В пользовательском config задайте `"adapter": "hc-codex"`. В локальном
`bindings/runtime.json` можно указать путь `hc_executable` и имя `hc_session`.
По умолчанию используются команда `hc` и сессия `default`. После изменения
настроек перезапустите MCP-сервер Workflow. CLI читает их при каждом вызове.

1. Вызовите `open TASK` без `--herdr-session` и сохраните RUN_ID. При `preparing` идёт подготовка. Затем
   `open TASK` или `run RUN_ID --compact` вернёт объект `hc`. В MCP у инструмента
   `run` параметры `id` и `compact: true`. Стадию запуска показывают `run_status`
   в `open` и `status` в `run`. Состояние терминала находится в `hc.terminal_state`,
   сигнал Codex — в `hc.agent_status.state`. До первого сигнала OSC 7501 поле
   `agent_status` равно null. При первом входе подтвердите доверие к знакомому
   репозиторию в Codex.
2. В Desktop подключитесь к сессии `hc.session` на машине исполнителя. Для удалённой
   машины используйте SSH. Найдите пространство `hc.space` и вкладку `hc.tab`.
   Desktop группирует терминалы по меткам `herdr.space` и `herdr.tab` из `terminal.get`
   и добавляет имя удалённой машины к локальным адресам.
3. Из консоли или панели Herdr TUI на машине исполнителя примените окружение
   `hc.attach.env`, удалите переменные из `hc.attach.unset_env` и выполните
   `hc.attach.argv` отдельными аргументами. Команда вида `hc attach CORE_ID/t1`
   адресует терминал в сохранённом core. Сохраняйте префикс CORE_ID при копировании:
   разные core могут иметь одинаковые имена сессий и локальные адреса `t1`.
   Если у клиента нет маршрута к этому core, hc сообщит об ошибке.
   Нажмите Ctrl+обратная косая черта для отсоединения. Повторный `open TASK`
   возвращает подключение к тому же диалогу.
4. Для своего клиента откройте `hc connect --session NAME` на выбранной машине.
   По одному JSON-RPC сообщению на строку запросите `server.status` с `{}`,
   сверьте `result.core.id` с `hc.core_id`, затем вызовите `terminal.get`
   с `{"terminal":"t1"}`, подставив `hc.address`. На клиентском core найдите
   в `machine.list` машину по этому core ID, используйте адрес вида `worker/t1`.
   Сверяйте `labels["workflow.run"]` с RUN_ID. Идентичность включает машину,
   сессию, core ID и локальный адрес. Схему методов возвращает `hc schema`.
5. Ответьте на отложенный вопрос через `answer TASK --text ...` и продолжите
   в этом диалоге с префиксом `TASK_ID: `. Ревью выполняет независимый subagent.
   Приёмка проверяет принадлежность терминала перед закрытием. Отмена сохраняет
   неопубликованный worktree по общим Git-правилам.

При `hc_access_denied` или `hc_unavailable` скопируйте команду из `next_action`
в `open` или `hc.next_action` в `run --compact`. Выполните её в обычной консоли
на машине исполнителя под тем же пользователем с доступом к hc. `hc_unavailable`
включает случаи, когда hc сообщает только о таймауте. `hc.terminal_state=unknown`
означает, что состояние терминала не удалось подтвердить. Статус запуска берётся
из записи Workflow. Ошибку старта исполнителя проверяйте по `current_startup_error`.

Чтобы вернуть создание новых задач в TUI, задайте `"adapter": "herdr-codex"`
и перезапустите MCP. Сохраните hc, его сессию и версию Workflow с обоими адаптерами
до завершения всех hc-запусков. Старые записи обслуживает прежний транспорт.
Для запуска legacy Herdr TUI из обычной консоли укажите `--herdr-session NAME`
перед `open`. Имя сессии показывает `herdr session list`.
После разрыва связи повторите `open`: проверка находит исходный терминал по
записанному намерению. При неподтверждённом исходе сохраните запуск до сверки
с исходным core. После потери процесса `--keep` может восстановить shell.
Проверьте его вручную, прежде чем закрыть и возобновить задачу из checkpoint.
