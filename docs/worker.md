# Инструкции исполнителю

Выполняй цель и критерии assignment.md. Прочитай проект и сохранённый план
по [planning.md](planning.md); покажи актуальный план в чате и сохрани до работы.
Ищи память выборочно через `memory-list --project ID --query 'тема' --limit 10`, не загружай
её целиком. Продолжай выдачу через --offset next_offset или уточняй запрос. При восстановлении сначала читай предыдущий checkpoint, затем
state.json, questions.json, progress.md и result.md, если они есть.

Используй полную команду control-workflow из задания с выбранными state/config/bindings:
текущий каталог, в том числе worktree, не выбирает экземпляр. Для progress,
block, finish и памяти своего запуска указывай --run RUN_ID. JSON состояния
меняй через CLI панели.

Код меняй только в перечисленных worktree; другой репозиторий или worktree
запроси в чате до редактирования. Исходные деревья сохраняй. Для применения
готовых настроек хоста запускай установщик из исходного checkout: постоянные
ссылки должны вести туда. Если отслеживаемые файлы не меняются, worktree не нужен.

Сначала найди пути и нужные разделы в области задачи, затем читай их с ограничением
вывода. Для пакета exec задай общий бюджет и лимиты отдельных команд; большие
независимые чтения разбей. После обрезания дочитай только потерянный нужный фрагмент.
Повторное чтение оправдано изменением источника, экземпляра или восстановлением
утраченного контекста; неизменённый документ используй из уже прочитанного.

Рано уточняй решения, влияющие на пользовательский сценарий, сначала проверив
сохранённые предпочтения. Продолжай разрешённую работу до результата или конкретного
блокера, уважая паузу пользователя и границы полномочий.

## Длительное ожидание

До запуска проверки или внешней операции выбери срок ожидания, путь лога вне
worktree и способ получить конечный результат: успех, ошибка, таймаут или отмена.
Один процесс выполняет ожидание и сохраняет лог и код завершения; в контекст
возвращай краткий исход и нужный фрагмент ошибки. Уведомление о завершении
используй, только если инструмент действительно его доставляет.

Например, для известного GitHub run при наличии GNU timeout:
`timeout 30m gh run watch RUN_ID --exit-status > "$RUN_DIR/ci-watch.log" 2>&1`.
RUN_DIR — каталог артефактов запуска; 30 минут — пример, срок выбирай по операции.
Сохрани код возврата сразу после команды: 0 — успех, 124 — таймаут timeout,
остальные — повод разобрать лог и итог внешнего run. Таймаут watch не отменяет CI.
`gh run watch` опрашивает GitHub внутри процесса; экономия требует ожидания
завершения с редкими возвратами к модели. Частый опрос процесса моделью её не даёт.

Если уведомлений нет, используй блокирующее ожидание в пределах лимита инструмента.
При вынужденных повторных вызовах выбирай максимально допустимый интервал,
сохраняя возможность ответить пользователю; частый цикл sleep/status через модель
не используй. Для выполнения из чата ограничь один блокирующий вызов 60 секундами,
если среда не требует меньшего интервала. При превышении общего срока прочитай
текущее состояние один раз и сохрани незавершённость и следующий шаг в checkpoint.
Ошибка ожидания не доказывает ни успех, ни остановку внешней операции:
сверь её состояние до повторного запуска; сбой исполнителя разбирай по [recovery.md](recovery.md).

При паузе пользователя прекрати зависимые действия и дальнейший опрос. Сохрани
checkpoint с идентификатором процесса/run, логом, сроком и способом продолжения;
явно укажи, продолжает ли внешняя операция работать. Останавливай её только
в пределах поручения и безопасным штатным способом. Отложенный вопрос и block
оформляй по [questions.md](questions.md); пауза не означает готовность.

## Проверки и сверка результата

Выбирай проверки по diff и критериям задания. Для документации проверь факты,
команды, ссылки и согласованность инструкций; для кода — затронутое поведение
и отказы. Обязательные проверки репозитория выполняй и при изменении только
документации. Сохрани команду, проверенную версию/diff, исход и лог.
Повтор полного набора требует причины: изменения затрагивают его результаты,
исправлен сбой, изменилась среда или этого требует репозиторий/приёмщик.
Укажи причину в отчёте и свяжи сохранённые результаты с новым diff.
После локальной правки сначала проверь затронутое; повтор полного набора на
неизменённом кандидате без новой причины не нужен.

Короткий итог по готовому отчёту сверь построчно с фактами и ограничениями.
Для правки небольшой страницы достаточно сверки исходника и diff; независимую
редакторскую сверку подключай при расхождениях или переработке структуры и смысла.
Редактура не заменяет проверку поведения кода. Если применяемый навык требует
более широкой сверки, выполни её и отметь дополнительный объём в отчёте;
общий навык самостоятельно не переписывай. Политику auto/manual и случаи
независимого ревью соблюдай по [agent-review.md](agent-review.md).

Совместимые изменения можно проверить на общем фиксированном кандидате и
применить одним rollout, если это входит в поручение. Сохрани состав, версию,
проверки и возможность отката; приёмка каждой задачи остаётся за её приёмщиком.
Изменение кандидата требует проверки затронутых частей и актуальности прежних
доказательств. Срочное исправление выпускай отдельно, не задерживая ради пакета.

## Работа и артефакты

Уточнения и координация — в чате или доступных прямых сообщениях агентам.
При вопросе, отложенном обсуждении или продолжении blocked читай
[questions.md](questions.md). При исчезновении исполнителя или ошибке запуска —
[recovery.md](recovery.md).

После значимых решений, изменений, проверок и результатов исследования
сохраняй полезные артефакты
в каталоге запуска рядом с assignment.md; краткое состояние — через
`progress --run RUN_ID --text 'Сделано; следующий шаг'`.
Обновляй существующий артефакт, если отдельная версия не нужна для проверки
или восстановления; не копируй переписку и неизменённые отчёты.
Перед паузой, передачей, отменой или после неудачи сохрани checkpoint:
сделанное, неоконченные изменения, проверки, причину остановки и следующий шаг.
Артефакты продолжения храни вне worktree: complete по умолчанию удаляет его
после подтверждённого Git-завершения во всех Git-режимах. Сообщение в чате не заменяет артефакты и статус панели.

Решение содержит контекст, выбор, причины, последствия и ссылки на изменения;
знание — проверенный факт и условия применимости. При замене прежней записи
укажи её ID и изменение. Для записи памяти вне итогового finish читай
[control-memory](../skills/control-memory/SKILL.md); без RUN_ID используй
memory-add без --run. Секреты и лишние полные логи в артефакты не записывай.

## Результат

В сообщениях о запуске и завершении называй целевой TASK_ID; перед ручной
командой укажи машину и затрагиваемый процесс. Различай обновлённый бинарник
и уже работающий процесс. После установки актуализируй итог отчёта; старые
отложенные пункты свяжи с дополнением.

После задания и обязательного auto-ревью покажи в текущем чате результат, изменения или выводы, проверки,
ограничения и вопросы. Для исследования изложи основные выводы и рекомендацию;
ссылки на подробности дополняют содержательный ответ.

Сохрани Markdown-отчёт: что сделано и как, изменённые файлы/ветки, команды
проверок и результаты, ограничения и оставшиеся вопросы. Если появились решения,
зафиксируй их отдельно с причинами. Готовый к review результат передай командой:

```sh
finish --run RUN_ID --report /path/report.md --decisions /path/decisions.md
```

--decisions необязателен. finish сохраняет отчёт и решения в запуск и память
проекта и переводит работу в review. При политике auto ответ содержит handoff:
сразу прочитай [agent-review.md](agent-review.md) и выполни независимое ревью
свежим subagent без истории переписки в этом же ходе. Это часть задания,
отдельное поручение управляющего не нужно. До заключения продолжай работу;
итоговый ответ и уведомление о готовности следуют после passed. При failed
или лимите возвратов покажи пользователю сбой либо оставшиеся замечания.
Если инструмент subagent недоступен, сохрани failed с этой причиной.
Отдельная копия через memory-add не нужна. Для незавершённой работы сохраняй checkpoint.

Самостоятельный finish оставляет review. Принимать и закрывать через complete
можно только по явному поручению пользователя: тогда прочитай
[control-complete](../skills/control-complete/SKILL.md) и
[git-policy.md](git-policy.md). Сохранение артефактов не означает приёмку.

При auto разрешены три автоматических возврата на задачу суммарно по всем запускам; четвёртый требует решения пользователя. После каждого исправления нужно свежее независимое ревью. При manual управляющий возвращает конкретные замечания тому же
исполнителю; при auto исполнитель получает их от subagent напрямую. Исправляй их в исходном объёме assignment.md, спорные требования
передавай пользователю. Повторный finish — в том же запуске после подготовки
возврата через review-feedback, даже если подтверждение доставки ещё не записано. Для no-code включи в finish повторяемый `--artifact PATH`
с файлами результата, чтобы проверяющий получил фиксированную версию.
Протокол: [agent-review.md](agent-review.md).
